## Findings per tool

### Beads and Gas Town

Beads: tickets as a dependency graph for agents. `bd ready` lists only unblocked
work and `--claim` takes it atomically; `bd prime` prints workflow context at session
start; `--deps discovered-from:<id>` records provenance. Workflow layer: a **formula**
is a TOML template (`[[steps]]` with `needs`, `{{var}}` variables, optional
`[steps.gate]`); `bd cook` compiles it to a **proto**; `bd mol pour` instantiates a
persistent **molecule** (an epic whose steps run in dependency order); a **wisp** is an
ephemeral molecule that is `squash`ed to one digest issue or `burn`ed. `bd ready
--mol <id>` is "what can run next inside this epic"; `bd mol progress` is
completed/total. **Gates** are issues that block dependents until an async condition
holds: `human` (only `bd gate resolve` closes it), `timer`, `gh:run`, `gh:pr`, `bead`;
`bd gate check` run from cron/CI closes the satisfied ones, and gated steps simply
stay out of `bd ready`, so agents never poll. Also: `defer`/`undefer`, `orphans`
(open issues referenced by commits), `epic close-eligible`, `preflight`, `doctor`.

Gas Town sits on top of Beads and orchestrates many agents: a Mayor decomposes work
into **convoys** of beads; `gt sling <bead> <rig>` assigns one to a worker (polecat)
in its own git worktree ("hook"); a per-rig **Witness** detects stuck agents and
nudges or hands off; a **Refinery** serialises merges through a Bors-style bisecting
queue with verification gates (polecats never push to main); a **Deacon**
supervises across rigs; `gt escalate -s CRITICAL|HIGH|MEDIUM` routes blockers to a
human; a **scheduler** caps concurrent polecats (`scheduler.max_polecats`) to avoid
API rate-limit exhaustion; `gt feed --problems` surfaces stalled and zombie agents.

**Worth stealing:** `defer`, `orphans`, formulas
as a *batch-with-variables-and-dependencies* idea, ready-within-an-epic, epic
progress, the `prime` pattern, gates *as a concept* (largely already covered, see
GAT note below). **For the runner (QST-2z8db), not core:** scheduler cap, watchdog
for stuck agents, resumable hooks (re-running continues the existing worktree), serialised
merges, severity-routed escalation.

**Not for us:** Dolt and any server/daemon, dotted child ids (parent/child stays
generic, EPC-1), mail/messaging and agent identities, `bd remember` persistent memory
(the Realm's `/memorize` and 03-knowledge own that), compaction/memory decay (round 1
already skipped it), wisps/ephemeral issues (questkit has no short-lived-issue
problem), the Mayor/Deacon/Witness role hierarchy (we need one agent per quest, not
a society), formula aspects and conditional bonds.

### TicGit

Tickets are git-meta data under a `ticgit:` namespace (`ticgit:tickets:<uuid>:title`
as string, `tags` as set, `comments` as list), exchanged via `refs/meta/*`. A ticket
exists when fields exist under its key, so there is no index file to conflict on.
Two-level lifecycle: broad `status` (open/closed) and specific `state` (open: new,
assigned, in-progress, blocked, **review**; closed: resolved, wontfix, duplicate,
invalid). Agent surface: `ti help --agent` prints a Markdown guide, `--markdown` renders
output with suggested next commands, `--json` has a written contract (JSON only on
stdout, diagnostics on stderr, no ANSI codes, non-zero exit on failure, schema
published at `docs/schema/v1.json`). `ti checkout <id>` sets a current ticket so later
commands omit the id. Saved views are static sets of ids. `ti import gh` one-shot
imports open GitHub issues.

**Worth stealing:** the written JSON contract with a published schema (AGT-2), the
`review` state (RUN-1), `help --agent` (AGT-1). **Not for us:** refs-based storage
(STO-2: it gives up Obsidian, Syncthing and grep, the core of questkit), UUID ids
(base36 ids are shorter and already prefix-resolvable), static saved views (questkit
views are queries, strictly better), `checkout` (id prefixes are already short), closed
sub-states (a terminal `scrap` plus `--log` reason covers it, and round 1 rejected
`duplicate_of`).

### tix-cli

Tickets are directories named by ULID inside `.tix/`, which is its own git repo;
attributes are files (`s=t` for status todo, `p=a` for priority); every operation is a
commit, so `undo`/`redo`/`log` come for free; projects are branches. Extensions are
any executable named `tix-<command>` on the PATH, with no plugin API. Status: 31
commits, last one 2025-09-03, UI "planned", README examples marked "not implemented
yet", docs inconsistent about sync versus pull/push. The root idea is captured below;
the project itself is not a source to track.

**Worth stealing:** git-style external subcommands (EXT-1). **Not for us:** attributes
as filenames and single-letter encodings (frontmatter is more readable and already
validated), nested-repo-per-log, undo/redo as a feature (a git revert does it, and
round 1 put git-derived history out of scope with REP-2).

### markdown-ticket (MDT)

Markdown files in the repo (`docs/CRs/`), project config in `.mdt-config.toml`,
numeric keys from a counter file (optional cloud allocation for shared numbering). A
drag-and-drop Kanban board with epic swimlanes and per-epic progress, an MCP server with
ten consolidated tools (`list_crs`, `get_cr`, `create_cr`, `update_cr_attrs`,
`update_cr_status`, `delete_cr`, `manage_cr_sections`, `suggest_cr_improvements`, plus
two project tools), and a spec-first slash-command chain (`/mdt:requirements` in EARS
format, `/mdt:bdd`, `/mdt:architecture`, `/mdt:tests`, `/mdt:tasks`, `/mdt:implement`
with per-task OK/FLAG/STOP verification, `/mdt:tech-debt`). A `research` ticket type
was added in v0.10.0.

**Worth stealing:** section-level read/write for MCP and CLI (AGT-3), the "tick off
per-task verification" idea as machine-visible progress (AGT-4), epic progress (EPC-1/2
inputs). **Not for us:** the web board (Obsidian Bases is the board; epic swimlanes
need EPC-1), the spec pipeline (that is Matt Pocock's skills plus `/implement-quest`),
counter-file numbering (questkit's random base36 ids are collision-free offline, which
a counter file is not), cloud allocation.

## Idea catalog

Each idea: suggested milestone, size, what it steals, shape, and the existing
quests it touches. Sizes: xs = schema/doc only, s = under a day, m = a few days.

### RUN - making unattended runs observable and safe

- **RUN-1 - A `review` status.** (0.5.0, xs) While a runner's PR is open the quest is
  neither "being worked" nor "done"; today it sits `in-progress`, which also makes
  `quest stale` lie. Add `review` between `in-progress` and `done` in the
  `development` schema vocabulary (schema authoring, no code). The runner sets it
  when the PR opens; [[QST-22gdn--commit-trailers-transition-quests-from-code-repos]]
  moves it to `done` on merge; `next` skips it. Steal: TicGit's `review` state.
  Check first: which views, Bases groupings and `readiness:` rules enumerate
  statuses.
- **RUN-2 - `defer_until` backoff.** (0.6.0, s) Optional date field; `next` and
  `ready` skip a quest whose date is in the future; `parked` stays for "indefinitely".
  Gives the runner failure backoff ("park until tomorrow") and humans "revisit after
  the release". Steal: Beads `defer`/`undefer`. Shares date-comparison machinery with
  [[QST-nij1y--due-derived-computed-fields-overdue-and-due-in-plus-a-due-view]], so do
  it after that.
- **RUN-3 - Attempt count for retry caps.** (0.5.0, xs) QST-2z8db wants "park after
  N failures". Simplest: a plain integer custom field `attempts` that the runner
  increments (zero core change), with `--where "attempts<3"` in the runner's
  selection. Only if more run facts (harness, model, session link, outcome) need
  querying, grow it into a computed field from `## Log` lines with a reserved `run:`
  prefix, using the same lazy-body machinery as criteria progress
  ([[QST-bo3xs--checklist-progress-computed-fields-criteria-done-and-criteria-total]],
  [[QST-vy4vt--body-as-a-lazily-loaded-queryable-field]]). Do not build the computed
  version speculatively.
- **RUN-4 - Orphan report.** (0.6.0, s, after QST-22gdn) Quests mentioned in commit
  messages or PR titles but still non-terminal: code merged, quest forgotten. Extends
  the trailer tool (`quest-apply-trailers --report`), not a core verb. Steal: Beads
  `orphans`. Catches runner PRs merged without a transition.

### CLM - claims (round 1's AX-4, re-examined)

- **CLM-1 - Reopen AX-4: verdict stays "not in core", trigger refined.** (decision
  only) AX-4 was rejected on 2026-08-22 with the trigger "the moment two agents can
  draw from `quest next` concurrently". The runner creates two different kinds of
  concurrency, and only one needs a claim:
  (a) *parallel subagents inside one epic run*: the coordinator is the single writer of
  quest files, so no claim is needed;
  (b) *two runner invocations* (overlapping cron ticks, laptop plus dev-01, a human
  running `quest next` mid-run): needs a claim.
  Options for (b): frontmatter claim fields with a TTL are advisory only, because
  Syncthing/git propagation latency is the race window, so they are unsafe across
  devices. **Branch-as-claim** is linearisable: the runner pushes
  `quest/QST-x-slug` to Gitea first and a rejected push means it lost the race; the
  git remote is the one linearisable store the Realm already trusts. Beads can offer an
  atomic `--claim` because a Dolt server serialises writers; Gas Town instead caps
  concurrency with a scheduler. Recommendation: the runner owns branch-as-claim
  (QST-2z8db decision 4); core adds nothing until a *second concurrent runner* is
  real. Revisit trigger: the first duplicate-run incident, or enabling any scheduled
  trigger with concurrency above 1.

### EPC - epics and the ticket graph

- **EPC-1 - Epic membership via the generic reference field.** (0.5.0, s on top of
  QST-698og) `/implement-spec`-style runs need "the children of this epic and which are
  unblocked". Today there is no parent field, and a finished epic such as QST-bmzl2 has
  `blocked_by: []`, so membership lives only in prose. v3 deliberately kept
  parent/child out, and round 1 redirected SCH-1 to a generic `type: ref` field
  ([[QST-698og--generic-reference-field-type-for-schema-declared-relations]]). This idea
  does not reopen a hardcoded hierarchy: the `development` schema would declare
  `epic: {type: ref}` using that mechanism, reverse refs are computed (as for
  `blocks`), and `quest next --where epic=QST-x` is the epic's frontier. Aggregates on
  the epic (`children_total`, `children_done`) are a new "computed over reverse refs"
  mechanism, same family as criteria progress. Steal: Beads `ready --mol`, `mol
  progress`, parent-child deps; MDT epic swimlanes. **Decision needed from Peter**
  (open question 1), because it touches a v3 decision.
- **EPC-2 - `closeable` epics view.** (0.6.0, xs after EPC-1) Epics whose children are
  all terminal, as a view. Steal: Beads `epic close-eligible`.

### WFL - recipes (Beads formulas, scaled down)

- **WFL-1 - Intra-batch references, then variables, then named recipes.** (a: 0.5.0, s;
  b/c: later, on evidence) Verified gap: in `quest new --batch -` ids are minted at
  creation and `blocked_by` accepts only existing ids, so an agent turning a spec into
  eight dependent tickets needs a second pass of `quest set blocked_by=...`. Steps:
  (a) optional local `key:` per batch entry; `blocked_by: [key-a]` resolves to the
  minted id inside the batch, validated as a DAG; (b) `{{var}}` templating with
  `--var k=v`; (c) named recipe files in the synced schema directory, `quest new
  --recipe release --var version=0.5.0`. (a) is independently useful and is exactly
  what `to-tickets`-style skills need; (b) and (c) wait until a template repeats
  (release checklist, [[QST-cv23q--quest-release-tag-and-push-a-version-in-one-command]],
  is the first candidate). Steal: Beads formulas (`needs`, `{{var}}`). Explicitly
  **out**: wisps, bond algebra, aspects, conditional bonds, `waits_for` fan-in.

### GAT - gates (verdict: no new concept)

Beads needs first-class gates because its issues cannot close themselves on external
events. questkit gets most of the value from pieces that exist or are planned: a
`hitl` quest *is* a human gate; "wait for the PR to merge" is a `blocked_by` on a quest
that QST-22gdn's trailers close on merge; "wait a day" is RUN-2. The remaining gap, a CI
run or PR state with no quest on the other side, has no demand yet. **Not proposed.**
Reopen if a runner flow needs to wait on something that cannot be expressed as a quest.

### EXT - extensibility

- **EXT-1 - Git-style external subcommands.** (0.5.0, s) When `quest foo` is not a
  builtin, exec `quest-foo` from the PATH with the resolved context exported
  (`QUEST_LOG`, `QST_ROOT`, schema path, questkit version, a contract version
  number). Builtins always win; `quest extensions` lists what is found; `quest doctor`
  ([[QST-whcdp--quest-doctor-diagnoses-environment-logs-and-installs]]) warns on a
  shadowed or non-executable `quest-*`. Steal: tix-cli's `tix-<cmd>` convention (also
  how `git` and `gh extension` work). Why it matters: it is the answer to QST-2z8db
  decision 1. The runner becomes `quest-run`, discoverable as `quest run`, while core
  grows by a dispatcher and gains zero worktree/Gitea/harness logic. It also gives
  SYNC-2's resolver, `quest-apply-trailers`, and the pages publisher
  ([[QST-97lsa--questkit-pages-publish-a-quest-log-as-a-static-website-via-a-github-action]])
  one consistent home. Risks: PATH execution (same trust model as git), and future
  builtin names colliding with installed extensions (hence "builtins win" plus the
  doctor check).

### AGT - agent surface

- **AGT-1 - `quest help --agent` (live guide instead of a generated file section).**
  (0.6.0, s after the QST-xlvml decision) AX-5 / QST-xlvml wrestles with managed
  blocks inside an existing AGENTS.md. TicGit (`ti help --agent`, `ti agent`) and
  Beads (`bd prime`) avoid generated text in files: AGENTS.md holds one pointer line,
  and the command prints the guide live from the merged schema (vocabulary, views,
  commit convention, report-back commands), optionally with a state tail (the caller's
  in-progress quests, the next ready one). Never stale, no managed block, no drift.
  Costs one tool call per session (or a SessionStart hook), so keep a short static
  AGENTS.md section as the fallback for harnesses that cannot run commands. Feed this
  into the QST-xlvml deep dive rather than a new quest.
- **AGT-2 - A written, versioned JSON contract.** (0.5.0, s-m) Verified gap: no
  documented guarantee. Consumers are about to multiply: the runner, the MCP server
  ([[QST-nxxk8--expose-questkit-as-an-mcp-server-with-purpose-specific-tools]]),
  `validate --format json` ([[QST-njwu7--machine-readable-output-for-quest-validate-via-format-json]]),
  `brief`. Steal TicGit's discipline: JSON only on stdout, diagnostics on stderr, no
  ANSI, non-zero exit on failure, a `schema_version` key, and JSON Schema files under
  `docs/schema/` for `list`, `brief` and `validate`, with a CI test that validates real
  output against them. Do this before the MCP server and runner harden against today's
  accidental shape.
- **AGT-3 - Section addressing.** (0.6.0, s) `quest show <id> --section Spec` reads one
  `## ` section; a subagent working ticket 4 of 8 does not need the whole file.
  Write side stays `--log` (QST-46rdv) plus AGT-4; add a general section writer only if
  those prove insufficient. Steal: MDT's `manage_cr_sections` and its consolidated
  ten-tool MCP design. Inform QST-nxxk8: tools should be section-aware from day one.
  Builds on QST-vy4vt.
- **AGT-4 - Acceptance write-back.** (0.5.0, s, after QST-bo3xs and QST-46rdv)
  `quest set <id> --check "<substring>"` ticks the single matching `- [ ]` under
  Acceptance (error if ambiguous or absent), `--uncheck` reverses. Read side is
  QST-bo3xs (`criteria_done`/`criteria_total`). Together the runner records per-criterion
  verification inside the quest, and "open the PR only when `criteria_done ==
  criteria_total`" becomes a machine-checkable gate. Maps MDT's OK/FLAG/STOP onto
  questkit primitives: OK = ticked, FLAG = a `--log` note and proceed, STOP = leave
  unticked and park. A flag on `set`, not a verb.

### STO - storage and where quest state lives

- **STO-1 - Where do quest edits land during a runner run? (design question, not a
  feature.)** Beads (Dolt), TicGit (refs), tix (nested repo) all keep tickets outside
  the code tree, which is why claims and status are instantly visible and never conflict
  with feature branches. questkit gave that up for Obsidian, Syncthing and grep. In a
  worktree flow it bites: a `status: in-progress` committed on the quest branch is
  invisible on main until the PR merges, parallel branches can conflict inside
  `quests/`, and a quest log can live in a different repo than the code. Options:
  (A) edits travel on the quest branch and land with the PR, so merge is what makes the
  state true (consistent with QST-22gdn, which transitions on merge) with branch-as-claim
  (CLM-1) covering visibility; (B) the runner commits quest edits directly to the log's
  main (visible at once, but touches a checkout the Realm convention forbids and risks
  main-over-open-PR conflicts); (C) only the coordinator ever edits quest files
  (implementers never do), which removes intra-epic conflicts under A. Recommendation:
  A plus C plus CLM-1's branch-as-claim; record it in QST-2z8db decision 4. Needs
  Peter's call (open question 3).
- **STO-2 - Refs-based or nested-repo storage. Rejected**, with the evidence that
  would reopen it: quest-file merge conflicts between parallel runner PRs that A+C
  does not prevent. Measure after the first twenty runner PRs.

5. **AGT-4** acceptance write-back (after QST-bo3xs, QST-46rdv) and **EPC-1** (inside
   QST-698og).
6. 0.6.0: AGT-1 (with QST-xlvml), AGT-3, RUN-2, RUN-4, EPC-2, WFL-1b/c on evidence.
7. Defer on triggers: CLM-1 (second concurrent runner), STO-2 (conflict evidence).
