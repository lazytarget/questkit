Ideas carry stable IDs (`SYNC-1`, `REL-2`, ...) for feedback by reference.
Grounded against `plan_questkit_v3.md` (0.3.0 nearly shipped) — nothing here
duplicates the v3 build order; items v3 explicitly rejected are marked as such
with the evidence that would reopen them.

## SYNC — Syncthing correctness

- **SYNC-1 — Conflict copies ARE enumerated as quests (verified bug).**
  Docs §10 claims a `QST-x...sync-conflict-....md` copy "will not be recognized
  as a quest at all", but Syncthing inserts the suffix *before* the extension, so
  the name still matches both `config.pattern` (`QST-*.md`, `list_cmd.py:322`)
  and `find_by_id`'s `{id}*.md` glob (`quest.py:234`) — confirmed with fnmatch;
  no exclusion exists anywhere in `src/`. A conflict copy shows up as a duplicate
  id in `list`, competes in id resolution (sorted-first wins), and would even
  pass `validate` (id prefix and self-alias both match). Fix: exclude
  `*.sync-conflict-*` at both enumeration sites, add a regression test, correct
  docs §10.
- **SYNC-2 — `quest conflicts [--resolve]`.** Detect conflict copies of quest
  files across logs, show a frontmatter-aware field diff against the original,
  and offer rule-based merge (e.g. newest `status_changed` wins per field),
  deleting the copy on resolve. questkit is the only tool that parses the
  format; today conflict resolution is raw-file eyeballing.

## QRY — query grammar

- **QRY-1 — OR across fields.** `--where` is OR-within-a-field, AND-across-
  clauses; there is no way to express `status=parked OR blocked=true`. Smallest
  grammar extension: a repeatable `--any "expr;expr"` group ANDed with the rest —
  no parentheses, no precedence rules.
- **QRY-2 — `quest search TERM`.** Full-text search over bodies across logs
  (bodies are invisible to `--where`), output as `id: matching line`, honoring
  the sweep root, ignore lists, and `--archived`. The `gh issue list --search` /
  grep-with-identity analog.
- **QRY-3 — `--group-by FIELD --count`.** One-call distributions
  (`quest list -A --group-by status --count`) instead of N `--where ... --count`
  invocations; the primitive REP-1 builds on.

## SCH — schema & rules

- **SCH-1 — Relation vocabulary: `relates_to`, `duplicate_of`.** Same design as
  `blocked_by` (stored one direction, computed reverse, qualified cross-log
  refs). `duplicate_of` gives QST-lc3d7's duplicate detection somewhere to point.
  Parent/child stays out, per v3.
- **SCH-2 — Checklist-progress computed fields.** `criteria_done` /
  `criteria_total` parsed from `## Acceptance Criteria` — progress becomes
  sortable/filterable (`--where "criteria_done>0"` = started), and Bases could
  show it. GitHub task-list progress analog; extends the reserved-names rule.
- **SCH-3 — Due-derived computed fields.** `overdue` (bool), `due_in` (days) +
  a `views.due`. Cheap (ISO strings already compare); might be what makes `due:`
  actually get used.
- **SCH-4 — Per-type readiness rules.** `when: "type=bug"` → require a
  `## Repro` section, in the `development` schema. The mechanism (`when:` reuses
  `--where`) already ships in v3 — this is schema authoring, not code.
- **SCH-5 — `unique: true` field constraint.** Log-wide uniqueness for a custom
  field (external ref keys, etc.), enforced by `quest validate`.
- **SCH-6 — Field deprecation.** `deprecated: true` on a schema field →
  `validate` notes it, `quest schema` marks it — a migration path gentler than
  deleting the declaration and having `strict: true` hard-error the corpus.

## AX — agent experience

- **AX-1 — `discovered_from:` lineage** (the steal from Beads). Agents doing
  work constantly surface side-work; `quest new --discovered-from QST-x` records
  provenance in one field, and `quest deps` gains a `--discovered` walk. Cheap,
  and it makes agent-filed quests auditable.
- **AX-2 — `quest ready <id>`.** The deferred-in-v3 predicate: evaluate
  readiness + state, exit 0/1, `--format json` listing failing rules. The
  missing shell primitive for `quest ready X && claude -p "$(quest brief X)"`.
- **AX-3 — `quest validate --format json`.** Machine-readable findings
  (file/rule/kind/message) so agents and CI act on findings without scraping
  stderr prose.
- **AX-4 — Claim/lease protocol (rejected in v3 — define the reopen trigger).**
  The moment two agents can draw from `quest next` concurrently, add advisory
  `claimed_by` / `claimed_until` (TTL) with `quest claim/release`, and `next`
  skips live claims. Until that's real, it stays out.
- **AX-5 — `quest init --agents`.** Generate an AGENTS.md section from the
  merged schema (vocabulary, views, commit convention, report-back commands) —
  same build-artifact philosophy as `_template.md`, but for agents landing in
  the repo.
- **AX-6 — MCP server / packaged skill.** Defer: the CLI is already
  agent-friendly, and `brief`/`schema`/`--format prompt` cover the needs. Revisit
  if a non-shell agent surface becomes real.

## CLI — commands & DX

- **CLI-1 — Shell completions** (bash/zsh/fish) with dynamic completion of ids,
  project names, and schema fields. Biggest daily-DX win per line of code.
- **CLI-2 — `quest edit <id>`.** `$EDITOR` on the resolved file; parity with
  `quest new --edit`.
- **CLI-3 — `quest log <id> "message"`.** Append a dated bullet to `## Log`
  (plus `--log` on `set`/`done`). The Log convention exists in every quest but
  nothing writes it except hand-editing; this is the write-back primitive both
  humans and agents lack.
- **CLI-4 — `quest open <id>`.** Open in Obsidian via `obsidian://` URI
  (fallback `$EDITOR`) — the `gh --web` analog.
- **CLI-5 — `quest doctor`.** One diagnosis pass: `QUEST_LOG`/`QST_ROOT` sanity,
  log discovery, duplicate ids, conflict copies (SYNC-1), hook-pin staleness vs
  questkit HEAD, uv-tool install currency. Multi-device setups rot silently;
  this is where the rot gets caught.
- **CLI-6 — User-level config** (`~/.config/questkit/config.yaml`): personal
  views/aliases and a default root — the `gh alias` analog. Small surface;
  per-log config stays canonical.

## GIT — hooks & code-repo integration

- **GIT-1 — Commit trailers close quests.** `Quest: QST-x done` or
  `Fixes: QST-x` in a code commit → a hook (or the realm-01 timer) applies the
  transition. This finally gives `git: manual` code repos the "one commit pairs
  code + ticket" flow the docs describe as the ideal — GitHub's closing
  keywords / Linear's auto-close, done offline.
- **GIT-2 — `quest develop <id>`.** Create branch `qst/x7k2m-<slug>`, set
  `status=in-progress` (the `gh issue develop` / Linear magic-branch analog).
  Pairs with GIT-3.
- **GIT-3 — `prepare-commit-msg` hook** suggesting the GIT-1 trailer from the
  branch name.
- **GIT-4 — Hook-pin refresh** — already tracked as QST-d8nu7 (99-system). Note:
  REL-4 makes pins human (`rev: v0.3.0`) and turns "bump the pin" into part of
  the release ritual.

## CMT — `quest commit` & the committer

- **CMT-1 — `quest commit --dry-run`.** Print the derived message and file list
  without committing — the timer's debuggability primitive.
- **CMT-2 — Body-only edits in the message.** A body edit with unchanged
  frontmatter should render as `~ QST-x body (+12/−3)` rather than an
  undescribed update (verify current behavior first).
- **CMT-3 — Committer heartbeat.** The timer writes `_committer.md` (last run,
  last commit, last error) — derived state, Syncthing-transported like
  `_validation.md`, so any device can see the unattended writer is alive.
- **CMT-4 — `--push` conflict policy.** Decide whether `--push` should
  `pull --rebase` first; an unattended pusher that stops on the first
  non-fast-forward is a silent history gap.

## REL — versioning, changelogs, releases

- **REL-1 — `quest changelog --milestone 0.3.0`.** Generate a Keep-a-Changelog
  section from terminal quests carrying that milestone, grouped by `type`
  (feature→Added, bug→Fixed, chore/task→Changed), title + id per line. Quests
  already are towncrier-style news fragments — the fragments exist (all 23
  stamped), only the renderer is missing. Works for *any* log with `milestone:`,
  not just questkit's.
- **REL-2 — `quest release <version>`** for questkit itself: verify every
  `milestone: <version>` quest is terminal, bump `pyproject.toml`, prepend the
  REL-1 section to `CHANGELOG.md`, `git tag v<version>`. Plus the retro-tags
  v3 §2 already flagged as worth creating (0.1.0, 0.2.0).
- **REL-3 — Milestone burnup.** `quest list --group-by milestone` (QRY-3) or a
  `views.milestone` showing open/done per bucket — "how far is 0.4.0" in one
  command.
- **REL-4 — Publish: remote + PyPI + tagged releases.** Unblocks CI-1, makes
  `pip install questkit` true, and converts hook pins from opaque shas to
  version tags (GIT-4).

## MOB — mobile & Obsidian

- **MOB-1 — `quest adopt` (inbox pattern for phone capture).** A file created
  from `_template.md` and saved as `NEW--<anything>.md` gets adopted by the
  committer timer: mint id, rename to canonical form, normalize, warn via
  `_validation.md`. Rename-at-birth doesn't violate filename immutability —
  identity begins at adoption. Answers QST-2zgfk without trusting Obsidian to
  mint ids.
- **MOB-2 — Templater id-minting** (QST-2zgfk's direct answer): random base36 in
  a template JS one-liner is trivial; risk is schema logic duplicated outside
  `validate`'s reach. Viable as MOB-1's complement (instant identity when it
  works, adoption as backstop).
- **MOB-3 — HA read surfaces.** Beyond the planned capture path: a `quest next`
  / stale-count sensor on the dashboard, and a notification when
  `_validation.md` is non-empty.
- **MOB-4 — Termux widget.** Home-screen prompt → `quest new` — CLI-grade
  capture on the phone for the person who does use a terminal.
- **MOB-5 — Obsidian plugin.** Explicitly deferred: Bases + generated template +
  adopt covers the family surface without owning a plugin.

## REP — reporting & statistics

- **REP-1 — `quest stats [--in|-A]`.** Distribution (status/type/priority),
  flow (created vs closed per week from `created`/`status_changed`), median age
  of open, draft backlog age. Text + JSON. The "declining engagement" signal
  that killed Trello, made visible early.
- **REP-2 — Git-derived history (research question).** `status_changed` keeps
  only the last transition; git history could reconstruct trends (cumulative
  flow) for `git: auto` logs. Worth a spike only after REP-1 proves current-state
  stats insufficient.
- **REP-3 — Weekly digest.** The timer writes `_digest.md` (new/done/stale per
  log this week) — derived state, phone-readable in Obsidian, zero new
  infrastructure.

## CI — automation

- **CI-1 — questkit repo CI** (needs REL-4's remote): pytest matrix
  (3.11–3.13), ruff, pre-commit, and on tag: build + publish + REL-1 changelog.
- **CI-2 — Reusable log-CI recipe:** `quest validate && quest format --check`
  for any public repo hosting a log (both commands already exist and exit
  correctly); realm-01's timer stays the private-side equivalent.

## INT — integrations

- **INT-1 — GitHub Issues one-shot import/export.** `quest import gh:owner/repo`
  via `gh` CLI for lazytarget projects going OSS. Deliberately not two-way sync
  (a tarpit; conflicting sources of truth).
- **INT-2 — ICS feed for `due:` quests** — `quest ics > quests.ics`, subscribable
  from any calendar.

## Comparison: questkit vs gh / GitHub Issues / Beads / Beans / Jira / Linear

### questkit vs `gh` — structural

| Axis | `gh` | questkit |
|---|---|---|
| Source of truth | GitHub's server, via API | local Markdown files |
| Offline | unusable | native; Syncthing carries state |
| Ids | `repo#N`, sequential, server-allocated | random base36, mintable anywhere offline |
| Interactivity | interactive prompts by default | never interactive, by design |
| Output | `--json` / `--jq` / `--template` | `--format json\|csv\|prompt` + `--select` (comparable) |
| Extensibility | `gh alias`, `gh extension` ecosystem | none (→ CLI-6) |
| Escape to GUI | `--web` | none (→ CLI-4) |
| Cross-repo view | `gh status` | `quest list -A` / `next -A` (stronger) |

### What questkit has that none of them do

Offline-first multi-device without a server; per-log schema with *ordered*
vocabularies driving sort; Obsidian as a first-class family surface; `quest
brief` (an agent work order — none of the compared tools has an equivalent);
validation that refuses to guess; readiness as configuration.

## Honest gaps (current)

No body search (QRY-2) · no OR across fields (QRY-1) · only the last status
transition survives (REP-2) · no release story — no tags, no CHANGELOG,
`pyproject` at 0.2.0 (REL-*) · no completions (CLI-1) · sync-conflict copies
leak into enumeration (SYNC-1, verified) · phone capture unanswered
(MOB-1/2, QST-2zgfk draft) · no remote/PyPI presence (REL-4).

## Recommended R&D emphasis (ordered)

1. **Ship 0.3** — QST-e6g6t and QST-5rjla are in progress; nothing above should
   preempt them. Fix **SYNC-1** immediately (small, correctness).
2. **The release loop: REL-1 → REL-4 (+ GIT-4).** Both halves of the
   versioning ask converge here, the `milestone:` data already exists, and tags
   fix the hook-pin problem as a side effect.
3. **Git loop closure: GIT-1/GIT-2/GIT-3 + CMT-2.** Removes the last manual
   pairing between code commits and quest state — the biggest daily-friction win
   for the `git: manual` code repos.
4. **Cheap DX/AX batch:** CLI-1/2/3, AX-2/3, CMT-1, QRY-3 — each small,
   each used daily.
5. **Phone capture: MOB-1 (+ MOB-2)** — the family log has 0 quests; capture is
   the proven strength, so extend it to the one surface where it's still absent.
6. **Defer until evidence:** AX-4 (claims), AX-6 (MCP), MOB-5 (plugin),
   INT-1 (GitHub sync), REP-2 (git-derived history).
